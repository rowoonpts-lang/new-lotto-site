# Development Guide

## 개발 원칙

- 기존 운영 기능을 유지한다.
- 변경 범위를 최소화한다.
- 한 번에 하나의 기능만 수정한다.
- 수정 전 반드시 현재 코드를 분석한다.
- 모든 변경 사항은 Git으로 관리한다.

## 작업 순서

1. 코드 분석
2. 문제점 분석
3. 영향 범위 확인
4. 개선 계획 수립
5. 코드 구현
6. 테스트
7. Git Commit
8. 문서 업데이트

## 브랜치 규칙

- feature/*
- fix/*
- refactor/*
- docs/*

## Commit Message 예시

- docs: add initial project documentation
- refactor: improve common library structure
- fix: resolve login session issue
- feature: add lottery statistics page

## 테스트 원칙

- 기존 기능이 정상 동작하는지 확인한다.
- 변경된 기능만이 아니라 관련 기능도 함께 테스트한다.
- 운영 환경 배포 전 로컬 또는 Codespaces에서 검증한다.

## 연쇄 영향 검증

공통 설정, 인증정보, 외부 서비스 연결정보를 변경할 때는
변경 파일 하나만 확인하고 작업을 종료하지 않는다.

핵심 변경과 직접 연결된 서비스와 설정은 같은 작업 단위에서
모두 확인하고 함께 검증한다.

예를 들어 데이터베이스 계정 또는 비밀번호를 변경할 경우
다음 항목을 확인한다.

1. PHP 데이터베이스 설정
2. 문자/OShot 등 별도 Agent의 데이터베이스 설정
3. Cron 및 배치 작업의 데이터베이스 연결
4. 배포 스크립트와 운영용 설정
5. GitHub Actions Secret 등 외부 자동화 설정
6. 기존 백업 설정에 오래된 인증정보가 남아 있는지 확인
7. 각 연결의 실제 로그인 또는 상태 확인
8. 관련 서비스의 실제 기능 회귀 테스트

변경 범위는 최소화하되,
변경 때문에 반드시 함께 수정해야 하는 연결 고리는 누락하지 않는다.

설정 변경 작업은 연결된 모든 서비스의 검증이 끝난 뒤에만
완료로 판정한다.
